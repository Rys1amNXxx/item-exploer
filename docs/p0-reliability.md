# P0 稳定性补强（0.1.2-dev）

## 存档保护规则

存档仍使用版本 1，0.1.0 / 0.1.1 的正常存档可以继续读取。
读取先验证临时库存，全部通过后才开放；不采取“跳过坏条目、保存剩余条目”的方式。
无 `Storage` 标签视为新设备；已经存在但没有版本号的 `Storage` 不视为空设备。

验证覆盖字段类型、格式版本、目录 / 条目数量、ID 唯一性、父目录存在性、循环与深度、
名称规范与同级重名、总容量、物品存在性、样本数量、NBT 大小、直接嵌套终端和同目录重复条目。
物品解码后重新保存的数据必须与原样本相同；无法无损读取的附加数据也会触发保护。
目录列表可以乱序，过小但为正的 ID 计数器会根据现有 ID 安全提升。

任一验证失败，整台终端进入只读保护状态：

- 客户端持续显示“数据保护中”，禁用存入、取出和目录修改按钮。
- 服务端及库存层同时拒绝修改，Shift 存入和鼠标携带物品不会被消耗。
- 原始 `Storage` 标签仍原样写回方块实体，错误的标签类型也保留。
- 未验证物品不进入可取出列表，也不会把其原始 NBT 发给客户端。
- 服务端日志记录失败原因、维度、位置和恢复文件路径。

## 恢复文件

服务端加载受保护设备时，会在 `<世界目录>/itemexplorer-recovery/` 写入独立的压缩 NBT：

| 字段 | 内容 |
| --- | --- |
| `Storage` | 原始存储数据，不做部分修复 |
| `Dimension` | 原设备维度 |
| `X` / `Y` / `Z` | 原设备坐标 |
| `Problem` | 验证失败原因 |

文件名为恢复内容的 SHA-256。相同内容与位置复用已经验证的备份文件；写入先使用临时文件，
再移动到最终路径。检测到已有文件被截断 / 改写时会报错，不把它当作成功备份。
备份失败不会清空原始数据；拆除方块前还会重试一次。独立备份成功后，即使设备被拆除，文件也保留。
受保护库存不会生成部分物品掉落。磁盘写入失败时应保留世界备份、不要拆除该设备；具体错误会出现在服务端日志。

恢复由服主在世界副本上进行，当前没有自动导入或自动修复命令：

1. 关闭服务器，复制完整世界目录以及 `itemexplorer-recovery/`，保留原文件。
2. 根据日志定位原因。缺失物品模组应先恢复对应模组；未知较新格式应使用支持该格式的版本，不能只改 `Version` 数字。
3. 目录 / 数量损坏时，根据备份核对原始物品总量和目录关系，离线修复世界副本的对应方块实体。
4. 如果原方块已经拆除，恢复文件中的 `Storage` 需要放回唯一一个目标终端；不要同时向多台终端导入同一份库存。
5. 在副本确认目录、数量和物品附加数据正确，再使用修复后的世界。保留原始备份以便复查。

仅重新加载仍有问题的数据不会解除保护；重新加载有效版本 1 数据后会自动解除。

## 自动验证与 CI

本地和 CI 都执行构建及独立的 GameTestServer：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\dev.ps1 build runGameTestServer --console=plain
```

新增测试在 `StoragePersistenceTests` 和 `StorageInteractionTests`。
覆盖保护状态及原始数据往返、归档写入失败、两个 FakePlayer 菜单交错操作、延迟旧请求、
菜单关闭与断线的鼠标物品归还 / 掉落、限流重置、目录被另一菜单删除和网络消息编解码。
区块测试在测试世界的远处加载设备，等待真实区块卸载，再从磁盘重新加载并比较库存。

`.github/workflows/verify.yml` 在 push、pull request 或手动触发时运行，使用 JDK 17 和项目 Wrapper。
GameTest 失败会使任务失败；日志始终尝试上传，JAR 仅在前序步骤成功后上传。
这份工作流不发布版本，也不包含测试世界或恢复数据。

## 真实多人验收（含 2026-09-29 补充结果）

早期 FakePlayer 和延迟调度测试仅验证服务端逻辑。2026-09-29 已补做两个实际 Forge 客户端到独立服务端的本机 TCP 验证，以及独立服务端重启；具体范围与证据见 [补充验收报告](acceptance-2026-09-29.md)。
使用独立测试世界、两个安装相同版本的客户端，记录双方背包 + 鼠标携带 + 设备 + 地面物品的总量。

| 场景 | 操作 | 验收标准 | 状态 |
| --- | --- | --- | --- |
| 同时取物 | 库存 64 个铁锭，两人同时请求取 48 个，再刷新重试 | 总量始终 64，无负数、重复或消失 | 本机真实 TCP 通过，旧请求重发也通过 |
| 延迟连续点击 | 分别在正常网络、约 150 / 300 ms 往返延迟下连续右键、Shift 点击、拖动 | 旧请求可被拒绝；提示后能重试，库存与背包最终一致 | 待执行 |
| 删除当前目录 | B 停留在空目录，A 删除它 | B 自动回根目录，可继续存取 | 待执行 |
| 关闭 / 断线 | 携带物品时关界面或断线；另测满背包 | 物品回背包或按原版规则掉落一次，总量不变 | 真实关闭后的旧请求已通过；携带物品和断线仍待执行 |
| 拆除 / 离开 | 操作期间另一玩家拆设备，或玩家离开可用范围 | 旧界面失效，后到请求不转移库存 | 待执行 |
| UI 保护提示 | 在世界副本放入未知版本的终端数据 | 保护提示完整可读，修改按钮禁用，玩家物品保留 | 本地盘大小窗口提示与禁用通过；完整携带物品交互仍待验收 |
| 重启与模组物品 | 存入附魔物品、带能量 / 自定义数据的模组物品并重启 | 数量、目录和物品附加数据不变 | 独立服务端及代表性 AE2 / MEK 物品通过，MEK 实际能量保持一致 |

按上表逐项记录通过范围，不将本机 TCP 测试扩大解释为真实网络延迟、断线或全部多人兼容性已验证。
