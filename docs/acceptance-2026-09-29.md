## 已确认问题

### NAS 失败提示遮挡第四盘位

复现：安装四块盘，填满玩家 36 格主背包，点击任意盘位的“弹出”。

实际：出现“背包已满，或数量为零”的错误条，覆盖第四盘位名称、数量以及安装 / 弹出按钮的一部分。库存没有变化，但用户暂时无法看清该盘位。普通错误提示约 4.5 秒后自动消失，重复触发会重新计时；这不是永久遮挡。

原因：`NasScreen.render()` 的错误面板底部固定为 `topPos + 134`，第四盘位为 `topPos + 111..137`、按钮为 `topPos + 114..132`，并且提示在更高图层绘制。

状态：**已实机复现，未修复。** [截图](verification/2026-09-29/nas-full-inventory-overlap.png)。

另有代码审查发现：受保护硬盘在 NAS 中不可提供 `volume()` 时，终端将其显示成普通“硬盘离线”，具体损坏 / 保护原因仅在其他设备界面可见。该诊断提示问题尚未完成本轮实机复现，不计作已通过。

## 真实双客户端 TCP

一个独立专用服务端（PID 30472）和两个完整 Forge Minecraft 客户端 DevA / DevB（PID 30540 / 39360）连接 `127.0.0.1:25589`。
两端使用不同 TCP 端口，客户端记录 `memoryConnection=false`，服务端断言玩家不是 FakePlayer。
测试客户端自动从收到的真实菜单快照构造生产 `StorageNetwork.request`；共享文件只协调发送时机，不传递库存或执行存取。

| 场景 | 服务端库存 / DevA / DevB | 结果 |
| --- | --- | --- |
| 初始 64，两人依据同一 revision 各取 48 | 16 / 48 / 0 | 一方请求过期被拒绝，数量守恒 |
| 双方重发原请求 | 16 / 48 / 0 | 陈旧请求无副作用 |
| DevB 根据新快照重试取 48 | 0 / 48 / 16 | 仅取出剩余 16，总数仍为 64 |
| 另补入 32，DevA 发原版关闭包后再发旧菜单请求 | 32 / 48 / 16 | 关闭后的请求无效，总数 96 与新增夹具数量一致 |

三进程均正常退出，退出码 0。证据：[阶段与连接记录](verification/2026-09-29/multiplayer-server.txt)、[退出记录](verification/2026-09-29/multiplayer-summary.txt)。
这覆盖实际客户端与服务端的本机 TCP 通信，但没有注入延迟，不代表 WAN、断线或所有多人操作已验收。

复跑：

```powershell
pwsh -NoProfile -File scripts/verify-multiplayer.ps1
```

脚本准备隔离启动参数后直接启动三个 JVM；需保留约 5–7 GiB 可用内存。客户端初始化后自动隐藏测试窗口并在完成后退出。
`-PrepareOnly` 只准备配置；之后可用 `-RunDirectory <准备目录>` 执行一次，已运行目录不可重用。
